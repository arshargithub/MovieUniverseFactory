### B1. Define a minimal reusable interface

Inspect existing camera/shot controls before implementing anything. If necessary, add only a small validated shot specification for the existing admitted world: source scene/version, existing timeline interval, camera framing/pose or supported follow parameters, and bounded render settings. Reject arbitrary code and unapproved file paths. Preserve one world-travel owner and existing animation/FX; no new gait or retiming solver.

Preparation may change trusted repository code, and must be counted as setup cost. It is not itself evidence of zero-code reuse. Reuse existing camera utilities; do not create a general scene DSL, service, agent framework, or new exporter. Cap setup at 20 active minutes within the 60-minute total. If a safe useful interface cannot be prepared, close this episode as `REUSE_INTERFACE_GAP` with a concrete backlog item.

Before the creative request, publish supported controls and freeze the implementation/source digest. Verify normal input and at least one out-of-contract rejection without touching the accepted scene. Keep baseline source files read-only; outputs go to a distinct episode directory.

### B2. Held-out shot and revision

After interface freeze, ask the Director for one new **3–5-second shot** from the existing world within the published control scope. The Director chooses the shot—not the implementation author before freeze. Reuse an interval of existing motion; avoid adding gameplay, actors, interactions, or effects.

Render a cheap complete preview. Then request one meaningful in-scope camera/composition revision after the Director sees it. Suitable examples: more forward room, a different subject scale, or a stronger destination reveal. Do not use an arbitrary speed change unless coordinated motion timing is already supported without a new solver. Do not manufacture a request after seeing what the implementation can produce.

For each operation, retain the structured request, source/version, expected changes, protected state, output, source digest, elapsed activity, native time, API cost, and any manual/code intervention. Natural-language interpretation may be assisted, but declare whether a human/supervisor translated it; do not claim autonomous direction.

### B3. Verify and close

- New shot and revision are complete clips, not only selected stills.
- Director confirms the requested framing change; preference for the revision is separate from instruction compliance.
- Admitted actor/world identities, source assets, and animation remain unchanged. Compare the relevant structured state and source hashes; do not require identical output pixels after a camera change.
- Unchanged runtime implementation digest from freeze through both requests establishes parameter-only reuse. Record all interventions, not merely Git commits.
- Relevant boundary tests pass. Reopen the derived scene and reproduce one selected frame if within the native budget. No whole-film rerender or full historical suite is required.
- Report setup, new-shot, and revision costs separately, with coverage limits. Do not compare a 3-second camera change against the whole first film as an equivalent workload.

If a post-freeze code change is required, the primary result is **reuse not demonstrated**. At most one repair is permitted inside the existing envelope, explicitly reported as code-assisted. A repaired replay of the same request does not erase the held-out failure. Do not launch another campaign to obtain a PASS.

Stop on the first exhausted resource ceiling, unsafe boundary, source/asset mismatch, or necessary out-of-scope change. Waiting for Director input ends active work and is recorded as waiting. No unattended continuation, spend increase, or additional experiment is implied.
