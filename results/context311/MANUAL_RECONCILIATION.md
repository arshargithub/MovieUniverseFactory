## Failure-seeking review

1. Hash checks alone could conceal a semantic omission. Original paragraphs are
   preserved exactly; applicability/core reconciliation is manual and finite test
   coverage is separately labeled, not proof of universal correctness.
2. Smaller core could simply move the same or more material into routed output.
   Measure core plus serialized route bytes for each frozen case; report expansion
   as expansion. No token, latency, render-time or quota-savings percentage follows.
3. Bounded output could hide an error in the middle. Scan full text for lexical
   signals, retain full stdout/stderr and actual exit, report omitted samples.
   No signal or exit0 is a semantic/quality pass. Agent must inspect ambiguous logs.
4. State recovery could revive old approvals. Fresh separate-process recovery must
   retain all four open defects, protected Pashtun and false modality flags. This
   is local state reconstruction, not proof of a fresh LLM session's behavior.
5. New bookkeeping could become another large mandatory context layer. Only core
   and applicable routes are defaults; coverage, preserved snapshot, tests and
   audit are evidence for changes/ambiguity, not required recurring full reads.
6. Helpers could be mistaken for automatic enforcement. They are opt-in commands,
   not app interceptors, semantic classifiers, secret scrubbers or a sandbox.
   Existing conversation/system/tool context remains outside their control.

These checks reduce specific failure modes, not eliminate model judgment errors.
